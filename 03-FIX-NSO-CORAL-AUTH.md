# Fix: nxapi NSO Coral Authentication (all three auth paths broken)

## The Problem

`nxapi nso auth` fails after Nintendo Account login. The Coral API requires an `f` token generated by a third-party service, and all three available providers are broken.

## Auth Path 1: Default (remote config selects provider)

```
Error: Remote configuration prevents Coral authentication
```

The remote config at `fancy.org.uk/api/nxapi/config` has `coral: null`, which tells nxapi not to attempt Coral auth. Setting `NXAPI_ENABLE_REMOTE_CONFIG=0` bypasses this but then falls through to imink (Path 2).

## Auth Path 2: imink fallback

```
ErrorResponse: [imink] Non-200 status code
    from https://api.imink.app/f (500 Internal Server Error)
      { error: true, reason: 'Something went wrong.' }
```

The imink API (`api.imink.app`) is returning 500. This is a third-party service that's currently down or broken. Not something we can fix.

## Auth Path 3: nxapi znca API via URL

```bash
NXAPI_ENABLE_REMOTE_CONFIG=0 ZNCA_API_URL=https://nxapi-znca-api.fancy.org.uk/api/znca nxapi nso auth
```

```
ErrorResponse: [znca-api] Non-200 status code
    from https://nxapi-znca-api.fancy.org.uk/api/znca/f (401 Unauthorized)
      { error: 'unauthorised', error_message: 'Missing request authorisation' }
```

The nxapi znca API requires OAuth client credentials. The npm release (v1.6.1) has embedded credentials that work when the remote config selects this provider normally. But when you force `ZNCA_API_URL` directly, the v1.6.1 code path doesn't send the client credentials with the request.

## What Needs to Happen

The cleanest fix: make Path 3 work by ensuring client credentials are sent when `ZNCA_API_URL` is set.

Look at `src/api/f.ts`:

```typescript
// This is the code path when ZNCA_API_URL is set:
export function getPreferredZncaApiFromEnvironment(options) {
    // ...
    if (process.env.ZNCA_API_URL) {
        return new ZncaApiNxapi(process.env.ZNCA_API_URL, options, options?.useragent);
    }
    return null;
}
```

The `ZncaApiNxapi` class has a `genf` method that calls the znca API. It needs to include client auth in the request. Look at how the default (remote-config-selected) code path constructs the `ZncaApiNxapi` instance vs. the `ZNCA_API_URL` path. The default path likely passes client credentials; the env var path doesn't.

Key things to find in `src/api/f.ts`:
- How `ZncaApiNxapi` sends authentication (look for `Authorization` header, `client_id`, `client_secret`, or `client_assertion`)
- Where the embedded client credentials live (look for `client_auth_provider`, `client_assertion_provider` imports)
- How the `getDefaultZncaApi()` function (the remote-config path) passes credentials that `getPreferredZncaApiFromEnvironment()` doesn't

The fix is probably just passing the same credentials object to the `ZncaApiNxapi` constructor in the `ZNCA_API_URL` branch.

## Alternative Fix

Inside the `data` field, the `coral_auth` section controls which provider is used:
```json

    "default": ["nxapi", "https://nxapi-znca-api.fancy.org.uk/api/znca"]

```

And `coral` is set to `null` (which blocks auth). If `coral` can be set to something non-null that allows auth to proceed, and the `coral_auth.default` provider is used with proper credentials, it might work.

The downstream project (slash-playtime) has a Switch presence poller that shells out to `nxapi nso presence --json` every 90 seconds to track what game is being played on Nintendo Switch. The code and tests are done (16 tests passing). It just needs this auth to work.

Parental controls auth (Moon API) works fine with the patches from 01 and 02. Only the NSO Coral auth is broken.
